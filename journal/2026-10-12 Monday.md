### What I learned
- `/etc/passwd` is the file that lists every user account on the system. It's world-readable (everyone can read it) because programs need it to map UIDs to usernames.
`darkhand:x:1000:1000:darkhand:/home/darkhand:/bin/bash`
	- It has seven fields separated by colons
	1. Username|`darkhand`|The login name
	2. Password|`x`|Placeholder — actual hash is in `/etc/shadow` which only root can read. In ancient Unix, this field held the hash directly — and since `/etc/passwd` is world-readable, anyone could copy and crack it.
	3. UID|`1000`|User ID (`0` = root, - `1–999` — system accounts (daemons, services), `1000+` — regular user accounts). There should only be one UID 0 account.
	4. GID|`1000`|Primary group ID. Secondary groups are in `etc/group`
	5. Comment|`darkhand`|Description (often full name, or empty)
	6. Home directory|`/home/darkhand`|Where the user's files live
	7. Login shell|`/bin/bash`|The shell that runs on login. Common shells: `/bin/bash`, `/bin/sh`, `/bin/zsh`.
- `/nonexistent` or `/` for system accounts that don't need a home.
- **System accounts** often have `/usr/sbin/nologin` or `/bin/false` — meaning they can't log in interactively.
- Detecting Anomalies in `/etc/passwd`
	For a security investigator, `/etc/passwd` isn't just a user list — it's a place to hunt for **backdoors**.

| Anomaly                                                | Why suspicious                                                           |
| ------------------------------------------------------ | ------------------------------------------------------------------------ |
| **Multiple UID 0 accounts**                            | Only root should have UID 0. Anything else is a backdoor.                |
| **Users with unusual home directories**                | `/tmp`, `/dev/shm`, or empty (`::`) — legitimate users don't live there. |
| **Users with valid shells who shouldn't have them**    | A service account with `/bin/bash` is suspicious.                        |
| **Recently added users**                               | Compare to a baseline. Check file mtime on `/etc/passwd`.                |
| **Users without a matching `/etc/shadow` entry**       | Account exists but isn't usable.                                         |
| **Empty password field** (not `x`, but actually blank) | Account can be logged into without a password. Catastrophic.             |
- What to do if I find a backdoor?

|Step|Command|What you're checking|
|---|---|---|
|Check if the account has a password|`sudo grep "sysadmin" /etc/shadow`|Does it have a hash? Is the hash crackable?|
|Check when it was added|`stat /etc/passwd`|When was the file last modified? Does that align with known activity?|
|Check if it's been logged into|`last sysadmin` or `lastlog -u sysadmin`|Has this account ever been used?|
|Check bash history|`cat /home/sysadmin/.bash_history`|What did this account do?|
|Check for a home directory|`ls -la /home/sysadmin`|Does it have one? What's in it?|
|Check running processes|`ps aux \| grep sysadmin`|Is it currently active?|
|Check SSH keys|`ls -la /home/sysadmin/.ssh/`|Does it have authorized keys for passwordless access?|
- This is where incident response discipline matters. **Don't just remove it.** The order is:
	1. **Preserve evidence first.** Screenshot, copy the relevant files to a secure location, log what you find.
	2. **Contain** — disable the account (`sudo passwd -l sysadmin` locks it without deleting).
	3. **Investigate** — find out how it got there. What else did the attacker do?  
	4. **Eradicate** — only after you understand the full scope.
	5. **Recover** — restore from a clean state if needed.
- If you just `userdel sysadmin`, you've destroyed evidence and you still don't know:
	- How the attacker got in.
	- Whether other backdoors exist.
	- Whether they still have access through another channel.
- The two commands to run to check on any suspicious /etc/passwd
	`awk -F: '$3 == 0 {print $1}' /etc/passwd`
	`awk -F: '$3 >= 1000 && $3 < 65534 {print $1, $3, $6, $7}' /etc/passwd`
- `/etc/shadow` is where the **actual password hashes** live. It's readable **only by root** (and sometimes the `shadow` group).
	Why separate from `/etc/passwd`?
		Because `/etc/passwd` is world-readable. If the hashes were in there, any user could copy them and crack them offline. Splitting the hashes into a root-only file enforces least privilege.
	`darkhand:$6$xyz123$longhashhere:19000:0:99999:7:::`
	**It consists of Nine fields, separated by colons (`:`).**

|#|Field|Example|Meaning|
|---|---|---|---|
|1|Username|`darkhand`|The account this entry belongs to|
|2|Password hash|`$6$xyz123$...`|The hashed password (or `!` / `*` if locked)|
|3|Last change|`19000`|Days since Jan 1, 1970 that the password was last changed|
|4|Min age|`0`|Minimum days before the password can be changed|
|5|Max age|`99999`|Maximum days before the password must be changed|
|6|Warn|`7`|Days before expiry to warn the user|
|7|Inactive|(empty)|Days after expiry before the account is disabled|
|8|Expire|(empty)|Days since Jan 1, 1970 that the account expires|
|9|Reserved|(empty)|Unused, reserved for future use|
- The password hash field is the most important fiels. It tells you the **hashing algorithm** and the **status** of the account.
	Format: `$id$salt$hash`

|Prefix|Algorithm|Security|
|---|---|---|
|`$1$`|MD5|**Weak** — should not be used|
|`$2a$`, `$2b$`, `$2y$`|bcrypt|Good|
|`$5$`|SHA-256|Acceptable|
|`$6$`|**SHA-512**|Current standard on most Linux|
|`$y$`|yescrypt|Modern, strongest|
|`!` or `*`|**No password set** — account cannot log in with a password||
|`!$6$...`|Account is **locked** but has a hash||
- `$1$` is MD5, which is weak and deprecated. Modern systems use `$6$` (SHA-512) or `$y$` (yescrypt). Seeing `$1$` on a modern server is a red flag: either the system is old, or someone deliberately set a weak hash.
- Never paste password hashes into an AI chat or any public place. Even though this is your own machine, the habit matter
