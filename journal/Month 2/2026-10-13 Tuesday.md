### What I learned
- One precision point to retain: `getent group` is usually better than reading `/etc/group` directly because systems can use directory services such as LDAP in addition to local files. Also, Docker-group access is effectively root-equivalent on a typical **rootful** Docker setup; it is not proof that every Docker configuration behaves identically.
- GTFOBins is a **curated list of Unix binaries** that can be exploited to bypass local security restrictions.
	**URL:** [gtfobins.github.io](https://gtfobins.github.io/)
	**Why it exists:** On any Linux system, there are hundreds of legitimate binaries. Some of them — if configured wrong (SUID, sudo, capabilities) — can be abused to:
	- Spawn a shell
	- Read arbitrary files
	- Write arbitrary files
	- Escalate to root
	GTFOBins documents exactly how each binary can be abused, under each configuration.
- When you look up a binary on GTFOBins, it's organized by **how** the binary is running with elevated privileges:

|Category|What it means|Example|
|---|---|---|
|**SUID**|The binary has the SUID bit set (runs as file owner, usually root)|`find / -perm -4000`|
|**Sudo**|The binary can be run with `sudo` (as configured in `/etc/sudoers`)|`sudo -l` shows it|
|**Capabilities**|The binary has Linux capabilities assigned (e.g., `cap_setuid`)|`getcap -r / 2>/dev/null`|

- The same binary might be exploitable under SUID but **not** under Sudo, or vice versa. It depends on how the binary is configured and what it can do.
- How to read a GTFOBins entry
	Go to [gtfobins.github.io](https://gtfobins.github.io/) and search for **`find`**.
	For SUID:
		./find . -exec /bin/sh -p \; -quit
		**What it does:** If `find` has SUID and is owned by root, this runs `/bin/sh` with root privileges (the `-p` flag preserves the effective UID).
	For Sudo:
		sudo find . -exec /bin/sh \; -quit
		**What it does:** If `find` is in your sudoers list, this runs a shell as root.
	For Capabilities:
		Not always applicable — depends on the capability.
- The three things every GTFOBins entry tells you
	1. **The category** — SUID, Sudo, or Capabilities.
	2. **The exploit command** — what you run.
	3. **What it gives you** — shell, file read, file write, etc.
- GTFOBins lists the same binary under SUID, Sudo, and Capabilities — because how the binary is elevated changes what exploit is needed. Under SUID, you sometimes need the `-p` flag to preserve root UID. Under Sudo, you don't. Same binary, different context.
- Why does the same binary have different entries for SUID vs. Sudo?
	Because **how the binary is elevated** changes what the binary can do with that elevation.
	**Example: `find`**
	**Under SUID:**
		`./find . -exec /bin/sh -p \; -quit`
		- `find` runs as root (SUID).
		- The `-p` flag on `/bin/sh` is **required** — without it, the shell drops privileges back to your user.
		- With `-p`, the shell stays root.
	**Under Sudo:**
		`sudo find . -exec /bin/sh \; -quit`
		- You run `find` via sudo.
		- No `-p` flag needed — sudo already gives the full root context.
		- The shell is root without needing to preserve effective UID.
	**Same binary. Different flag. Different mechanism.**
	That's why GTFOBins lists them separately. The exploit command depends on **how** the binary got elevated.
- SUID makes the binary run with the **file owner's effective UID** for the entire execution of that binary. Not "for a time" — for as long as the binary runs. **What `-p` actually does:** When a SUID binary spawns a shell, the shell normally **drops privileges** — it resets the effective UID back to your real UID, for security. The `-p` flag tells the shell **not to drop** those privileges. So:
	- `./find . -exec /bin/sh -p \;` → shell keeps root UID (because `-p` prevents the drop).
	- `./find . -exec /bin/sh \;` → shell drops back to your user.
	**Under Sudo**, you don't need `-p` because sudo already establishes a full root context — there's no effective UID to drop.
- On a clean Ubuntu/Mint system, most SUID binaries are legitimately safe (`passwd`, `sudo`, `su`, `mount`, `umount`, `chsh`, etc.). The dangerous ones are unexpected — like `vim`, `find`, `awk`, `nmap`, or any scripting interpreter with SUID set.
- VirtualBox has had privilege escalation CVEs in the past (e.g., CVE-2019-2525). Keep it updated. But in their default configuration, these are expected.
- Chrome and Chromium-based browsers use SUID sandboxes to isolate tabs. The SUID bit is required for the sandbox to work.
- The pattern for investigation
	When you run `find / -perm -4000 2>/dev/null` on a system you're investigating:
	1. **Compare to a baseline.** On a known-clean system, you know what's expected.
	2. **Look for the unexpected.** Any binary that doesn't belong — especially text editors, scripting tools, or unusual programs — is suspicious.
	3. **Check each unexpected one on GTFOBins.** If it has a SUID shell escape, it's exploitable.
	4. **Check timestamps.** `ls -la` on a suspicious SUID binary — when was it created? Does that match system install time?
- A SUID binary should **never** live in a user-writable directory. It should be in `/usr/bin`, `/usr/sbin`, or `/usr/lib` — owned by root, writable only by root.
- `mount` needs SUID so users can mount filesystems (like USB drives, ISOs) that require root to mount.
- `umount` needs SUID so users can unmount filesystems they mounted.
- Without SUID, mounting would require `sudo` every time.
	The risk: `mount` can be abused if not carefully restricted. That's why `/etc/fstab` exists — it defines which mounts are allowed without a password.
- Permission patterns in `ls -la` for SUID binaries (e.g., `r-s--x--x`).
### Commands/code worth remembering
```code
find / -perm -4000 -exec ls -la {} \; 2>/dev/null | head -10
- This shows the full permissions and timestamps of each SUID binary.
```
