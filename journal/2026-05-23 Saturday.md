### What I learned
- Running `sudo` seeks to use the privilege of root hence a security check is  performed to ensure you are the who you say you are and have the permission to act as root
- `sudo` doesn't just give root privilege instead it consults a file called `/etc/sudoers` to know exactly who can run what as whom. It's tied closely yo the the `principle ofleast privilege` in which a user is granted permission to only run some specific commands without giving them full access.
- The command `sudo -l` list all the possible commands a user is allowed to run with `sudo`. It is also one of the commands an attacker runs when they get access to a user account as it reveals every possible privilege escalation path
```
User darkhand may run the following commands on darkhand:
    (ALL : ALL) ALL
    (root) NOPASSWD: /usr/bin/mintdrivers-remove-live-media
    (root) NOPASSWD: /usr/bin/mintdrivers-load-broadcom-modules
    (root) NOPASSWD: /usr/bin/mint-refresh-cache
    (root) NOPASSWD: /usr/lib/linuxmint/mintUpdate/dpkg_lock_check.sh
    
The ALL tells me that I can run every command with root privilege however the other rootNOPASSWD says no password is required to run those as root hence they are potential privilege escalation path.

When you see `sudo -l` output, for each entry ask:
1. Is the script **writable** by my user?
2. Does it call **external commands** that can be hijacked via `PATH`?
3. Does it use **libraries** that can be injected via environment variables like `PYTHONPATH`, `PERL5LIB`, etc.?
```
- The reason only the root user and the shadow group have access to the `/etc/shadow` is because they contain password hashes that can be cracked offline
- Running the `cat /etc/shadow` gives results in the form `root : x : 0 : 0 : root : /root : /bin/bash`
```
|1|root|Username|
|2|x|Password placeholder (real hash is in /etc/shadow)|
|3|0|**User ID (UID)** — the number the system uses to identify you|
|4|0|**Group ID (GID)** — your primary group|
|5|root|Comment field — usually a description or full name|
|6|/root|Home directory|
|7|/bin/bash|Default shell|

Now, the two zeros: the first `0` is the **User ID (UID)**. The kernel doesn't actually care about your username — it uses the UID to determine permissions. UID 0 is special: it's the superuser. The kernel grants UID 0 unrestricted access to everything. The second `0` is the **Group ID (GID)** — group 0 is the `root` group.

So root is UID 0 and GID 0. That's what makes root, root.
```
- `/etc/passwd` gives the attackers a list of the user accounts that are available along with their home directories and their shells.  if a user's shell is `/bin/bash` (or another full shell), that user can log in interactively. If it's `/sbin/nologin` or `/bin/false`, that account is likely a service account that can't be used for a direct shell — but could still be exploited through a running service.
- A user that has UID 0 has unrestricted access to everything basically functions as root. An attacker can exploit this by creating a user account with such privilege to maintain persistent access even when password has been changed. This is classic backdoor technique.
- Attackers able to read your log reports is very dangerous. The `adm` group can read `/var/log/auth.log` and other system logs without root privileges. An attacker with `adm` access can silently harvest:
	- Usernames that exist on the system (from successful/failed logins)
	- IP addresses of trusted hosts
	- Authentication patterns (e.g., "does the admin login from home at 2 AM?")
	- Possibly passwords — if a user accidentally types their password into the username field, it gets logged in plaintext
	All without running a single privileged command or triggering a single alert. It's pure intelligence gathering, and intelligence is what turns a foothold into a full compromise.
