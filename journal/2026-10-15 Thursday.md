## Feedback: Question 3 is wrong. Let me correct it.

You said:

> _"cp /etc/cron.daily/backup.sh /tmp/backup.sh && chmod +s /tmp/backup.sh. The first part copies the sh file to tmp while the other sets suid bit on it so I can keep running it as root."_

**This is not the exploit.** Here's why:

1. **You're copying the script itself.** The script isn't a shell or an interactive program. Even if it had SUID, running it wouldn't give you a root shell — it would just run whatever the script does.
    
2. **Linux ignores SUID on shell scripts.** For security reasons, the SUID bit on a shell script doesn't work the way it does on a binary. The kernel won't elevate privileges for a script.
    
3. **`/tmp/backup.sh -p` wouldn't do anything useful.** The `-p` flag is for shells (like bash), not for arbitrary scripts. And the script isn't a shell.
    

**The actual exploit:** You edit the cron script to **add a line** that creates a SUID root shell. You don't copy the script — you modify it.

**The correct line to add to `/etc/cron.daily/backup.sh`:**

bash

cp /bin/bash /tmp/rootbash && chmod +s /tmp/rootbash

**What each part does:**

- `cp /bin/bash /tmp/rootbash` — copies the bash binary (a real executable, not a script) to `/tmp/rootbash`
    
- `&&` — only proceed if the copy succeeded
    
- `chmod +s /tmp/rootbash` — sets the SUID bit on the copy
    

**Wait for cron to run the script as root.** Root creates `/tmp/rootbash` with SUID set and owned by root.

**Then you run:**

bash

/tmp/rootbash -p

- `/tmp/rootbash` is a SUID copy of bash, owned by root.
    
- `-p` preserves the effective UID (root).
    
- You get a root shell.

### What I learned
- Never paste real credentials into any AI tool or public channel.
- `strings` + `grep` is a real technique for extracting readable text from binaries.
- Cron runs commands as **root** on a schedule.
- If a cron script is writable by a lower-privileged user, that user can **borrow root's trust** — without ever having root.
- `cron` is Linux's **scheduler**. It runs commands automatically on a timer. You write a "crontab" (cron table) entry, and the system runs that command at the specified time — every day, every hour, every 5 minutes, whatever you set.
- A cron entry has **five time fields** followed by the command:
	`* * * * * /path/to/command`
	│ │ │ │ │
	│ │ │ │ └── Day of week (0-7, 0 and 7 = Sunday)
	│ │ │ └──── Month (1-12)
	│ │ └────── Day of month (1-31)
	│ └──────── Hour (0-23)
	└────────── Minute (0-59)
- Special characters

|Character|Meaning|Example|
|---|---|---|
|`*`|Every value|`*` in minute = every minute|
|`,`|List of values|`1,5,10` = minutes 1, 5, and 10|
|`-`|Range|`1-5` = minutes 1 through 5|
|`/`|Step|`*/5` = every 5th value|

|Cron entry|Meaning|
|---|---|
|`0 3 * * *`|Every day at 3:00 AM|
|`*/5 * * * *`|Every 5 minutes|
|`0 0 1 * *`|Midnight on the 1st of every month|
|`0 9 * * 1-5`|9:00 AM, Monday through Friday|
|`30 14 * * 0`|2:30 PM every Sunday|
- Where crontabs live

|Location|What it is|
|---|---|
|`/etc/crontab`|System-wide crontab (includes a **user** field)|
|`/etc/cron.d/`|Additional system cron jobs (also include user field)|
|`/etc/cron.daily/`, `/etc/cron.hourly/`, `/etc/cron.weekly/`, `/etc/cron.monthly/`|Scripts run daily/hourly/weekly/monthly|
|`/var/spool/cron/crontabs/`|Per-user crontabs (one file per user)|

- **Important difference:** System crontabs (`/etc/crontab`, `/etc/cron.d/`) have **six fields** — five time fields plus a **username**. The command runs as that user.
- **Format of `/etc/crontab`:**
	`* * * * * user command`
	│ │ │ │ │ │    │
	│ │ │ │ │ │    └── The command
	│ │ │ │ │ └────── The user to run as
	│ │ │ │ └──────── Day of week
	│ │ │ └────────── Month
	│ │ └──────────── Day of month
	│ └────────────── Hour
	└──────────────── Minute
	**That extra user field is where the privilege escalation lives.** If a cron entry says `root /path/to/script.sh`, and you can edit `script.sh`, you run code as root.
- `crontab -l` -> This shows **your** crontab. If you've never added one, it'll say `no crontab for darkhand`
- **Day of week numbers:**
	- 0 or 7 = Sunday
	- 1 = Monday
	- 2 = Tuesday
	- 3 = Wednesday
	- 4 = Thursday
	- 5 = Friday
	- 6 = Saturday
- Concept 1: Why Writable Cron Scripts Are Dangerous
	- Cron runs scripts on a schedule. Some of those scripts run as **root**. If a script runs as root, and a **lower-privileged user can write to it**, that user can change what root executes.
		The Trust Chain -> Think of it this way:
		1. **Root trusts the script.** Root says, "Every night at 3 AM, I'll run whatever is in `/etc/cron.daily/backup.sh`."
		2. **Root doesn't check the script before running it.** It just runs it. Every time. Unconditionally.
		3. **If you can edit that script**, you're writing instructions directly into root's schedule.
		You never had root. But root runs **your** code because root blindly trusts the script.
		**This is the same pattern as SUID and `$PATH` hijacking** — a privileged process trusts an artifact that a lower-privileged actor can tamper with.
	-  The Classic Exploit — Line by Line
		`cp /bin/bash /tmp/rootbash && chmod +s /tmp/rootbash`
		**What each part does:**

|Part|What it does|
|---|---|
|`cp /bin/bash /tmp/rootbash`|Copies the bash binary to `/tmp/rootbash`|
|`&&`|Only run the next command if the copy succeeded|
|`chmod +s /tmp/rootbash`|Sets the SUID bit on the copy|
	- **The result:** `/tmp/rootbash` is now a SUID copy of bash, **owned by root** (because cron ran the script as root). Now anyone can run: `/tmp/rootbash -p`. The `-p` flag preserves the effective UID (root). You get a root shell. **Wait for the next cron cycle. Root shell. No exploit code needed.**
- Concept 2: Why This Happens (Misconfigurations)
	- Cron scripts should **never** be writable by anyone except root. On a correctly configured system:
		- `/etc/crontab` — owned by root, writable only by root.
		- `/etc/cron.d/` — root-owned, root-writable.
		- `/etc/cron.daily/` — root-owned, root-writable.
		- Individual scripts inside — root-owned, root-writable.
	    If any of those are writable by a non-root user, that's a **misconfiguration**. And a **privilege escalation vector**.
	- **Real-world reasons this happens:**
		- An admin ran `chmod 777` on a cron script to "fix permissions."
		- An installer created a script with incorrect ownership.
		- An attacker with temporary root access made a script writable before losing root, planning to come back.
- Concept 3: The Detection Command
	The roadmap says:
> _"find /etc/cron_ -writable 2>/dev/null and understand why a writable cron script is dangerous."*

	`find /etc/cron* -writable 2>/dev/null`

| Part              | What it does                                                        |
| ----------------- | ------------------------------------------------------------------- |
| `find /etc/cron*` | Search every path starting with `/etc/cron` (files and directories) |
| `-writable`       | Match files/directories writable by the current user                |
| `2>/dev/null`     | Suppress error messages (permission denied)                         |
	- **What "writable" means here:** `find -writable` checks whether the current user has write permission. So if you're running it as `darkhand`, it finds anything `darkhand` can write to. **On a correctly configured system, this returns nothing.** No user should be able to write to cron files.
- The Trust Chain Pattern

|Mechanism|How root's trust is borrowed|
|---|---|
|SUID|Program runs with file owner's permissions|
|`$PATH` hijacking|SUID binary calls a command without full path — attacker's version runs as root|
|**Cron**|Root runs a script on schedule — if writable, attacker's code runs as root|
	**Same underlying idea:** A privileged process trusts something. If a lower-privileged user can modify that trusted thing, they borrow the privilege without ever having it.
- Linux ignores SUID on scripts. You don't copy the script. You **modify** it to add: `cp /bin/bash /tmp/rootbash && chmod +s /tmp/rootbash`. Then run `/tmp/rootbash -p` for a root shell.
- `-p` is for shells, not arbitrary scripts. The correct command is `/tmp/rootbash -p` (where `rootbash` is a copy of bash).
