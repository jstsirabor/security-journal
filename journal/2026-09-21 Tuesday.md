### What I learned
- `$PATH` is an **environment variable**. It's a list of directories that the shell searches when you type a command. When you type `ls`, the shell doesn't magically know where `ls` lives. It looks in the directories listed in `$PATH`, in order, and runs the first `ls` it finds.
- If an attacker can modify `$PATH`, they can make your shell run **their** version of a command instead of the real one. **Example:** A SUID binary (running as root) calls `ls` without using the full path (`/bin/ls`). It just calls `ls`. The shell looks in `$PATH`. If the attacker has placed a malicious `ls` in a directory that comes **before** `/bin` in `$PATH`, the SUID binary runs the malicious `ls` as root. This is called **`$PATH` hijacking** and is a real privilege escalation technique.
- `$PATH` hijacking: If a SUID binary calls a command without the full path (e.g., `system("ls")` instead of `system("/bin/ls")`), an attacker can place a malicious version of that command in a directory earlier in `$PATH`. The SUID binary runs the malicious command as root. Defense: SUID binaries should always use full paths for any command they call.
- `$PATH` is a colon-separated list of directories the shell searches for commands. `which` shows where a command lives. `which -a` shows all matches. Order matters — the first match wins. Attackers can hijack `$PATH` to make a SUID binary run their malicious command as root. Defense: SUID binaries use full paths; root's `$PATH` excludes `.` and world-writable directories.
- The attacker doesn't need you to run their command directly. They need you to run a SUID binary that _indirectly_ runs their command because it didn't use a full path.
