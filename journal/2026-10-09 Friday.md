### What I learned
- `sudo` stands for **SuperUser DO**. It lets an approved user run a single command as **root** (the superuser), typically after typing their own password.
- `sudo apt install htop`
	Three things happen:
	1. **The system checks if you're allowed to use `sudo`.** It looks at a configuration file (`/etc/sudoers`) to see if your username is listed.
	2. **It asks for your password** (not root's password — yours).
	3. **It runs the command as root.** For that one command only. Then it's over.
- Why does `sudo` matter?
	Without `sudo`, you'd have to log in as root directly to do administrative tasks. That's dangerous:
	- **No audit trail.** Everything you do is logged as "root" — you can't tell who did what.
	- **No per-command boundary.** You have full root access until you log out.
	- **No password check on each action.** Root can do anything without re-authenticating.
- `id` tells you who you are — your user ID (UID), group ID (GID), and all groups you belong to.
	Output looks like:
	uid=1000(darkhand) gid=1000(darkhand) groups=1000(darkhand),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),...
	- Reading the output

|Part|Meaning|
|---|---|
|`uid=1000(darkhand)`|Your user ID is 1000, username is `darkhand`|
|`gid=1000(darkhand)`|Your primary group is 1000 (`darkhand`)|
|`groups=...`|Every group you belong to|
- Why a security person cares about `id`
	- **UID 0 is root.** If `id` shows `uid=0(root)`, you're root. Anything else is a normal user. 
	- **The `sudo` group.** If you're in the `sudo` group, you can run `sudo` commands. If not, you can't.
	- **Group memberships determine access.** If you're in the `adm` group, you can read log files. If you're in `docker`, you can effectively become root (Docker daemon runs as root). Each group is a potential privilege.
- `sudo -l` lists **exactly which commands you're allowed to run with `sudo`**, and under what conditions.
		User darkhand may run the following commands on darkhand:
	    (ALL : ALL) ALL
	Or, for a restricted user:
		User bob may run the following commands on darkhand:
	    (root) /usr/bin/systemctl restart nginx
	    (root) /usr/bin/apt update

| Part                                      | Meaning                                                       |
| ----------------------------------------- | ------------------------------------------------------------- |
| `(ALL : ALL) ALL`                         | User can run any command as any user/group. Full sudo access. |
| `(root) /usr/bin/systemctl restart nginx` | User can run **only** that one command as root.               |
- Why `sudo -l` matters for security
	This is **the most important command for privilege escalation detection**.
	If an attacker gets a normal user account, the first thing they check is `sudo -l`. Why?
	- If `(ALL : ALL) ALL` — they can become root instantly. Game over.
	- If restricted to specific commands — they look for **dangerous commands** in the list. For example:
	    - `sudo vim` → escape to shell via `:!bash`    
	    - `sudo less` → escape to shell via `!bash`
	    - `sudo find` → escape via `-exec`    
	    - `sudo awk` → escape via `system()`        
	Any command that lets you spawn a shell or read/write arbitrary files is a privilege escalation vector. GTFOBins lists them all.
- `sudo` normally caches authentication for a short timeout, so it does not necessarily request your password for every single command.
